# Canonical managed capture under implementation

LD-AI-001/002/004 and LD-REPO-003 retain native launch, authorship and
AgentStore/ThreadStore authority. E-AI-078 extends the native worker path to an
existing canonical conversation. E-AI-089 resumes the essential local v0
integration below; full provider/restart qualification and original M10.2/M13.3
gates remain open.

## Explicit preparation and launch

The bounded main-window command accepts the current vault/backend handle,
original preparation request, selected thread, observed source selection and
closed Codex client selector. Native code resolves the committed conversation
purpose, exact opaque or recorded-session target, repository and writable
lifecycle. Annotation, stale-selection and unavailable/closed source requests
fail. No original creation record or conversation UUID alias is required.

An idle plan retains its canonical identity, physical/backend binding and
observed selection. It owns no counted call, actor, journal or provider process.
Original and canonical plans share the existing sixty-four-plan capacity and
request namespace. A request cannot switch preparation type, client, thread or
observed selection. Repeated preparation returns the same target, including
after its launch grant is spent. Plans remain native window/generation/owner
state; they are not a conversation database or restart/resume authority.

The opaque target authorizes one attempt with the already verified native Codex
profile. Source, owner and physical admission are rechecked when claiming it; a
failed or lost startup cannot refund the grant. The synchronous launch hook
validates this retained grant rather than attempting an asynchronous graph read.
A process may begin initialization before current graph validation, but no
captured output or prompt may cross the worker's membership/privacy/store fence.
Resume and renderer-supplied roots, executable, environment, actor, repository
or target authority remain denied.

## Worker-owned initialization and publication

The E-AI-077 worker owns the complete processor operation. Canonical graph
reads, native privacy setup, explicit device-actor allocation, journal opening,
scanning and publication run there. Current writable membership must match the
prepared canonical identity before opening its capture sink. Private creation
cache loss cannot turn this identity into a file conversation or prevent an
otherwise valid new participation. Physical/backend replacement still rejects.

The sink retains the existing native capture formats, sanitizer, journal and
exact receipt fence. Its ThreadStore view validates the exact snapshot returned
to the sink: repository, thread and conversation-purpose target must match. The
unchanged native atomic binding carries that same observed header into
publication. A preceding check on another pin, parsing an opaque selection or
matching only a thread ID cannot substitute for this validation. The wrapper
delegates the real provider's publication capability and exposes no independent
ThreadStore write/status path; no alternate store or authority is introduced.

Incoming output from an already initialized provider remains capturable after
archival so that an in-flight reply is retained. Each capture still validates
the exact canonical membership. New prompts, including context-only prompts,
require current writable membership; archival does not authorize another turn.
Failure retires the worker with no raw fallback or automatic replay. Tombstoned
membership refuses further capture, including on the exact sink pin.

## Human prompt preparation

Before dispatch, native code confirms the prompt's nonempty human text using the
canonical writer. Worker and canonical UUID request identities remain exact.
Injected context and controls do not create human messages. Unknown/missing
confirmation prevents dispatch and retains the original intent/status identity.

New worker-owned human writes resolve current committed membership. A repeated
request recovers its retained original observed selection, sanitized intent and
receipt; metadata advanced by capture cannot make it a new write. Changed text
or identity fails. The renderer's direct canonical append remains strictly bound
to its supplied observed selection. Both paths share the existing native
sanitizer, domain-separated message identity and one-publication recovery.

The renderer adapter validates the returned original request and full canonical
target/thread/repository, retaining the separate opaque launch target. It sends
only the thread/selection/client preparation fields, never executable authority,
and performs no automatic preparation retry or worker launch.

## Remaining integration

E-AI-082 drafts a native device-private dispatch journal, adapting JJ Store's
retained-intent boundary. Canonical conversation content stays in
AgentStore/ThreadStore. The journal owns only local execution intent, sanitized
prepared context and native runtime observations. It binds one human request,
exact canonical identity/source/backend, native owner and one through four
distinct recipient requests before issuing any launch target. Authored turns
require the original confirmed native human proof; context-only turns require
its absence. A current outstanding request blocks another dispatch for that
thread. Repeated Begin returns retained state without granting a new attempt.

Native preparation reserves each target durably before the synchronous launch
hook may consume its in-memory grant. Restart/rebinding cannot recreate a spent
or uncertain grant. Native worker initialization binds its exact worker/open
request. Before a prompt leaves, the worker checks the original parent request,
authorship and stop fence, then retains sanitized text/context plus an exact
input digest. Terminal observations follow confirmed native capture; renderer
reports cannot assert completion. Unknown outcomes remain unresolved and never
replay. Discovery/status is read-only and returns path-free local observations,
not a substitute for canonical captured content or provider receipts.

Explicit Stop first records its irreversible fence, prevents late launch/prompt,
then closes the exact known workers and releases their in-memory plan entries.
It never refunds a target or undoes provider work. A failed close retains the
original request for explicit retry. New backend owners may inspect/stop old
intents for the same physical source; they cannot resume their dispatch. Native
filesystem/graph/privacy/journal work remains on the command/capture workers.
These sources remain unqualified; ordinary composer adoption, legacy managed
profile retirement, relocation recovery and full restart acceptance stay open.

The renderer validates a bounded path-free native view, records Begin before
preparing any target, and always includes that parent request during new turn
preparation. A retained Begin cannot reconstruct a launch attempt. Completion
requires the native capture observation, including after a renderer send reply
is lost; a resolved renderer send alone leaves delivery unknown. Exact or active
status reads never write or resume a dispatch. Stop survives IPC abandonment
under native transition ownership. Failed cleanup retains the original request
for explicit retry. A separate native fence precedes waiting for owned startups
and detaching renderer streams. Native Stop then closes known workers. Only its
confirmed result retires local subscription bookkeeping, including a lost detach
reply, without a second native close. Old Stop cannot clear a newer active
request. Current-owner checks prevent a surviving unclaimed plan from being
launched through a replacement backend handle.

Native stopped state confirms the irreversible dispatch fence and closure of
known sessions/processing authorities. An opening slot may not yet appear in the
public host session list; its later factory/prompt must still fail the retired
plan or persisted fence. This is not proof that every initialization process has
exited. Cold opening/close/retiring-worker qualification and full launch-plan
lifetime remain separate required gates. The Begin frame alone may reach 8 KiB
for four Unicode recipient preferences; ordinary frames keep 4 KiB and
authored-message frames retain their existing 1 MiB limit. Only participant and
prompt/context content passes through privacy; native request IDs, input digests
and bindings remain exact. Private intent v1 files are bounded to 4 MiB and use
the existing owner-only atomic/fsynced profile IO.

## Durable request claims and plan lifetime

E-AI-083 drafts owner-only `canonical-dispatch-requests-v1` claims for parent
and recipient request IDs. A domain-separated binding covers the native owner,
source/backend, canonical identity, observed selection and original input. A
recipient claim also seals its one target. Parent claims precede journal
publication; recipient claims precede target publication. An orphan claim is an
unknown prior attempt and cannot mint another target. A missing journal with a
retained exact claim is unavailable, not an absent turn. Claims are bounded to 1
KiB each and do not contain transcript text, credentials or paths.

A journal-backed plan transfers ownership to its native processor once and is
removed from the volatile queue during that transfer. Processor allocation or
initialization failure never refunds it. The journal and request claim keep the
original target and unresolved state. Preparation can read that retained target
without requiring the obsolete graph selection or installing another grant, even
when the sixty-four-slot queue is full. Newly reserved targets still require a
current selection and available capacity. Active runtime and capture limits
remain unchanged. Explicit Stop and native scope teardown retain worker cleanup
authority independently of the removed plan.

Legacy/capture-only preparation rejects a request already held by a durable
parent or recipient claim. Begin also refuses conflicting live legacy plans.
Claims survive backend closure and cannot be silently reclassified under a new
handle. Unqualified earlier draft journals without the required claims fail
closed; this source change performs no implicit migration, repair or replay.
Other legacy execution paths remain a separate retirement/adoption gate. Cold
lifecycle, cross-view/restart and actual provider qualification remain
unexecuted; this draft does not complete either native AI milestone.

## Local desktop v0 scope

E-AI-089 resumes essential live integration for local testing. Ordinary ACP
sessions remain available with their existing file persistence. Native JJ
conversations are explicitly selected and augment those sessions. The embedded
AppShell, shared composer, saved agent profiles/avatars, inline removable agent
references, automatic follow-up tags, model/effort controls and recorded source
picker are used by the native live panel. The first managed profile is Codex
ACP; unsupported clients are not advertised as executable native recipients.

A send confirms one canonical human write before launch, presents live output,
and replaces it with canonical captured history only after every started
worker's exact request is observed on the replacement pin. Failed reconciliation
keeps both the prior pin and live rows; explicit Stop retries cleanup and
reconciliation without resending. Unknown human writes retain their original
read-only receipt check. Exact approval options require acknowledgement. An
unsupported question is disabled with a neutral explanation and Stop available.
View-local drafts survive switching native threads while that panel is mounted.

The v0 intentionally defers native queues, attachments/context, slash commands,
skills/memory/handoff, full native message editing, a live people directory,
additional managed clients, per-thread durable drafts, durable renderer-intent
recovery after restart, broad matrices, real-provider fault/restart
qualification and signed distribution. These remain M10.2/M13.3 follow-up gates;
local build and focused tests do not complete those milestones. The initial
launch is for explicit testing, with no automatic replay after uncertain work.
